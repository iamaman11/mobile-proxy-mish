# Cloudflare integration boundary

This directory contains the two direct Cloudflare integration surfaces used by `mobile-proxy-mish`.

## Mesh / Zero Trust verification

The live Windows/Cloudflare Mesh prerequisites are verified through the official Cloudflare API by:

```text
.github/workflows/cloudflare-live-preflight.yml
```

That workflow is read-only and checks the accepted Windows profile, Mesh CIDR, device TCP/UDP/virtual-IP settings, and WARP-to-WARP connectivity. Cloudflare remains the live configuration authority.

## Remote-rotation control Worker

The authenticated remote-rotation control plane lives under:

```text
infra/cloudflare/control-worker/
```

It is deployed directly with Wrangler and owns only:

- the `mish-device-control` Worker;
- one fixed-name `DeviceControl("primary")` Durable Object for this single-device deployment;
- the control hostname `api.alegria.by`;
- the Worker secret `MISH_MANAGER_TOKEN`.

The Android device authenticates with its non-exportable Keystore P-256 key. The primary Durable Object stores the enrolled public identity and bounded operation correlation. Proxy credentials are not part of this control plane.

### Public manager API

The external manager has exactly one rotation operation:

```text
POST https://api.alegria.by/v1/rotate
Authorization: Bearer <MISH_MANAGER_TOKEN>
body: empty
```

The manager does **not** supply or retain `device_id`, `request_id`, `operation_id`, polling URLs or WebSocket details. The Worker generates the internal request id, routes to the single primary broker and waits event-driven for the existing PRODUCT result.

Every manager response uses `mish.control.rotate/v1` and contains the same typed fields:

```text
schema
request_id              # generated by the Worker; support/correlation only
terminal
result                  # CHANGED | UNCHANGED | FAILED | REJECTED | UNKNOWN
reason                  # strict reason enum
operation_id
changed
device_online
dispatched
retryable
timing.started_at_ms
timing.completed_at_ms
timing.duration_ms
```

`UNKNOWN` is reserved for transport/timeout uncertainty after the system may have accepted the command. It is deliberately non-retryable so a remote client cannot accidentally create a second rotation.

The device-side protocol is unchanged:

```text
ROTATE_IP(request_id)
 -> ACCEPTED(request_id, operation_id)
 -> RESULT(request_id, CHANGED|UNCHANGED|FAILED|REJECTED, operation_id?)
```

The privileged enrollment endpoint remains an operator/LAB provisioning seam and is not part of the remote application's business API.

## Boundary

There is no second configuration engine, mutable mirror, device registry, manager polling loop, offline command queue, Workers VPC dependency, Android inbound listener, second rotation owner or second PRODUCT state database. Mesh verification and control-Worker deployment stay independent.
